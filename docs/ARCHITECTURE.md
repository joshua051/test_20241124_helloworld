# Architecture

## Design constraints

1. Runtime combat code must not depend on Editor code.
2. Arena orchestration must not own player input.
3. Enemy attack concurrency is centrally governed by `ArenaDirector` attack tokens.
4. Crowd scoring is independent from individual attacks and exposes events for rewards.
5. Prototype geometry is reproducibly generated by `PrototypeBuilder`.
6. Production art and animation are explicitly deferred until the combat loop passes validation.

## Runtime responsibilities

- `Combatant`: health, invulnerability, hit stun, death lifecycle.
- `PlayerGladiator`: local input, locomotion, guard, dodge, prototype melee query.
- `EnemyGladiator`: approach/orbit/attack state and token lifecycle.
- `ArenaDirector`: wave lifecycle, enemy registration, attack-token arbitration.
- `CrowdFavorSystem`: favor accumulation and threshold rewards.
- `ThirdPersonArenaCamera`: orbit/follow camera only.
- `PrototypeHUD`: debug visibility; not production UI.

## Prototype debt accepted for v0.1.0

- `Physics.OverlapSphere` is used instead of animation-bound weapon hitboxes.
- Character visuals are primitive capsules.
- Enemy locomotion uses direct `CharacterController` steering rather than NavMesh.
- Input uses Unity's legacy Input API to minimize first-boot dependencies.
- No production save system, audio, animation graph, equipment inventory, execution system, or accessibility layer yet.

These are intentional vertical-slice shortcuts, not production architecture commitments.
