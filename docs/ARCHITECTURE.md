# Architecture

## Design constraints

1. Runtime combat code must not depend on Editor code.
2. Arena orchestration must not own player input.
3. Enemy attack concurrency is centrally governed by `ArenaDirector` attack tokens.
4. Crowd Favor, style scoring, weapon tuning, and combatant health are separate responsibilities.
5. Pure rules that do not require Unity scene state should remain testable as plain C# (`StyleScoreModel`, `WeaponCatalog`).
6. Prototype geometry is reproducibly generated by an explicit `PrototypeBuilder` menu action; no domain-load scene mutation is allowed.
7. Documentation may only claim implemented behavior, and implemented behavior may only be marked validated after real Unity evidence.
8. Production art and animation remain deferred until the graybox combat loop passes functional and feel gates.

## Runtime responsibilities

- `Combatant`: health, invulnerability, hit stun, death lifecycle.
- `PlayerGladiator`: local input, locomotion, guard, dodge, lock-on selection, prototype melee query.
- `PlayerWeaponController`: current weapon state, durability, pickup/swap lifecycle.
- `WeaponCatalog`: deterministic weapon tuning and arena weapon selection; pure/testable.
- `WeaponPickup`: world pickup representation and consumption.
- `EnemyGladiator`: approach/orbit/attack state, held weapon, drop behavior, token lifecycle.
- `ArenaDirector`: wave lifecycle, enemy registration, attack-token arbitration, routing style awards into Crowd Favor.
- `StyleScoreModel`: pure combo/variety/kill scoring rules.
- `CombatStyleSystem`: Unity-time adapter around `StyleScoreModel`.
- `CrowdFavorSystem`: favor accumulation and threshold rewards.
- `ThirdPersonArenaCamera`: orbit/follow behavior plus lock-on framing.
- `PrototypeHUD`: debug visibility only; not production UI.

## Data flow

```text
Player input
  -> PlayerGladiator
      -> PlayerWeaponController / WeaponCatalog
      -> EnemyGladiator.ApplyDamage
          -> Combatant lifecycle
          -> enemy death -> WeaponPickup
      -> ArenaDirector.RegisterPlayerHit
          -> CombatStyleSystem -> StyleScoreModel
          -> CrowdFavorSystem -> threshold reward -> PlayerGladiator.Heal

EnemyGladiator
  -> ArenaDirector.TryAcquireAttackToken
  -> PlayerGladiator.ApplyDamage
  -> ArenaDirector.ReleaseAttackToken
```

## Prototype debt accepted for this branch

- `Physics.OverlapSphere` is used instead of animation-bound weapon hitboxes.
- Character and weapon visuals are primitives.
- Enemy locomotion uses direct `CharacterController` steering rather than NavMesh.
- Input uses Unity's legacy Input API pending local Active Input Handling verification.
- Guard is omnidirectional in the graybox prototype.
- Camera has no obstruction/collision solver yet.
- Weapon catalog is code-defined rather than ScriptableObject-authored.
- Immediate wave transitions have no presentation state machine.
- No production save system, audio, animation graph, inventory UI, execution system, accessibility layer, or gamepad support yet.

These are deliberate vertical-slice shortcuts. They must not silently become production architecture commitments.
